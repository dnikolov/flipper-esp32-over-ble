# Capability registry

Connected ESP32 boards advertise an authenticated capability registry using the `capability_response` message defined in [PROTOCOL.md](PROTOCOL.md). Capability strings are stable lowercase ASCII identifiers using underscores. A board only advertises a capability it actually has the hardware for — see the phased roadmap in [PLAN.md](PLAN.md) step 7 for when each capability ships.

## Capabilities

- **`wifi_scan`** — Wi-Fi network scan, manually triggered by the Flipper user (a "Scan now" action, not automatic/periodic). Reports up to 32 discovered APs (the strongest by RSSI, if more are found), each with SSID, BSSID, RSSI, channel, supported PHY generation (802.11b/g/n/ax, collapsed to the highest generation the AP advertises), and auth mode. Results are shown on the Flipper's screen only — nothing is persisted or exported to SD card; that remains `wardriving`'s job. The ESP32-C6 has one 2.4GHz radio only (no 5GHz radio), so there is no separate "Wi-Fi 6 scan" mode — PHY generation is a per-AP property surfaced in the scan result, not a distinct scan operation. Uses the generic `command`/`status` message types — see [PROTOCOL.md](PROTOCOL.md)'s "`wifi_scan` command and status payloads" section for the exact wire shapes. Rejected `busy` if `wardriving`'s Wi-Fi source is currently active (one physical radio, one caller at a time).
- **`ble_scan`** — passive BLE advertisement scan, manually triggered by the Flipper user, mirroring `wifi_scan`'s "Scan now" pattern. Reports up to 32 discovered devices (the strongest by RSSI), each with address, address type, RSSI, and advertised name if present. Results are shown on the Flipper's screen only, nothing persisted. See [PROTOCOL.md](PROTOCOL.md)'s "`ble_scan` command and status payloads" section. Rejected `busy` if `wardriving`'s BLE source is currently active.
- **`wardriving`** — composite capability, advertised once the board has at least one of `wifi_scan`/`ble_scan` present. **Location data now comes from a real UART/NMEA GPS module** (hardware-verified 2026-09-13). `start`/`stop` are never gated on a GPS fix — `wardriving` always starts for its existing reasons only — but any record captured while the `gps` capability is not reporting `state = "fix"` is discarded (not logged to flash, not streamed), continuously, so losing a fix mid-capture pauses logging until it returns. The Flipper's wardriving control screen reflects this cosmetically via its Start action's label ("Start" vs. "Start (delayed)", read from the same `gps` status the fix icon uses) — the action itself behaves identically either way. A `command` to start it takes `sources` (`["wifi"]`, `["ble"]`, or both), `wifi_interval_ms`, and a `ble_window_ms`/`ble_interval_ms` pair in its `arguments` (a source the board does not have is rejected `invalid_command`); a `command` to stop it takes just an `action`. **The Flipper's wardriving screen lets the user pick which of these sources to request before pressing OK** (Left/Right toggle Wi-Fi/BLE membership, added 2026-09-11, offered only when the board advertises both `wifi_scan` and `ble_scan` — a single-source board has nothing to pick and always requests its one source, matching the original behavior); defaulting to both sources selected reproduces the pre-2026-09-11 always-request-everything behavior for anyone who never touches the toggle. `wifi_interval_ms`/`ble_window_ms`/`ble_interval_ms` remain fixed at their documented defaults — there is still no interval-entry UI. Interval bounds come from the radio-coexistence validation in [PLAN.md](PLAN.md) step 4, not a guessed value; the default itself is no longer step 4's most-aggressive point across the board — `ble_interval_ms`'s default was raised from 30ms to 500ms on 2026-09-10 after real wardriving traffic on real hardware showed 100% BLE duty starves the connection itself, and `ble_window_ms`'s default was separately raised from 30ms to 100ms the same day after a short test run showed a real chance of missing every nearby BLE device's advertisement at the resulting ~6% duty (`wifi_interval_ms` still defaults to its original point-4 value) — see [PROTOCOL.md](PROTOCOL.md) for the exact fields and current defaults. Capture runs autonomously once started — it continues across BLE disconnects and does not require an active Flipper connection to keep buffering, backed by a checksummed append-only circular log on a dedicated flash partition. Connecting drains the buffered backlog first (unsolicited, not waiting for a Flipper command — see PROTOCOL.md's `request_id = 0` convention), then streams live results. Because raw NOR flash can only be erased a whole sector at a time, "drop oldest when full" evicts a full sector's worth of records at once (tens of records in a batch), not strictly the single oldest record — see PROTOCOL.md's "Flash log eviction" note. Results captured while the location driver is not reporting a fix will be discarded once real GPS lands, per the fix-dependency design noted above (a Flipper-settable backfill-to-first-fix option — buffering and retroactively backfilling pre-fix records instead of discarding them — remains backlogged as an alternative, not chosen for this design) — not applicable today since the stub always reports a fix. `FirstSeen` timestamps will switch from the RTC-anchored backdating approximation described below to the new `utc_timestamp_s` wardriving-record field (see [PROTOCOL.md](PROTOCOL.md)) once that design is implemented, for any record carrying it. Data is transmitted as a compact CBOR record over BLE; the Flipper converts to WiGLE CSV only when writing to its SD card, as a single fixed-name file, `wardriving/wardriving_current.csv` (Phase 6, [WARDRIVING_PUBLISH.md](WARDRIVING_PUBLISH.md), superseding the former one-file-per-calendar-day naming `wardriving/wardriving_YYYYMMDD.csv` fixed 2026-09-12, same subdirectory both before and after), appended to via `FSOM_OPEN_APPEND` across however many sessions/days happen between publishes and only renamed away by the publish flow's host script after a confirmed successful upload — the WiGLE header is written only when that file is genuinely empty, written incrementally as records arrive (not buffered in RAM — a capture session may run for hours). The raw CBOR stream and flash log record every observation exactly as seen (no dedup at that layer); the CSV export layer alone collapses redundant repeats of the same address (`flipper/wardriving_csv.c`'s `feb_wardriving_dedup_should_write()`, added 2026-09-10): a row is written when an address is new to the export file, its RSSI improved by >= 6dB since its last written row, or it has moved >= 30m since then (that last clause is real but inert today — real GPS hasn't landed yet, so distance from the fixed-coordinate stub to itself is always 0). **Dedup scope is the CSV export file's own lifetime, not a narrower per-restart segment within it**: the same file stays open and the same dedup table keeps accumulating across any manual stop/restart of the `wardriving` command during one connection (a `"started"` ack never resets it) — both are reset together on disconnect/profile-teardown/app-exit (`reset_scan_ui_state()`'s `wardriving_csv_close()` call), which — since the BL03 fix above widened the on-disk file to per-calendar-day rather than per-connection — no longer necessarily coincides with the on-disk file's own lifetime: a same-day reconnect reopens (not recreates) the prior file, but starts the in-memory dedup table empty again, so an address already written earlier that day can be re-logged as "new" after a reconnect (a duplicate row, not a duplicate header — `docs/BACKLOG.md` tracks widening dedup scope to match the file's calendar-day scope as a follow-up). This was fixed 2026-09-11 (formerly `docs/BACKLOG.md` G29): resetting the dedup table on every restart made every address still in radio range look brand-new again, defeating the whole RSSI-improvement/movement policy and producing duplicate rows for unchanged addresses. A bounded 256-entry table tracks this for the file's whole lifetime; it evicts its oldest entry (not LRU) if the file sees more than 256 distinct addresses, which only softens dedup quality for an unusually address-dense run, not a correctness issue. `FirstSeen` timestamps in the exported CSV are reconstructed from the ESP32's boot-relative `timestamp_ms` by anchoring the newest drained record to the Flipper's current clock and backdating the rest — this board has no real-time clock, so exported times are an approximation, not a true wall-clock record. **The ESP32-local pre-log filter has the same scope rule, for the same reason**: `wardriving_dedup.c`'s per-address table (which gates what actually gets appended into the flash-backed circular log itself, not just the CSV export) is no longer reset by the `wardriving` command's start/stop handlers (fixed 2026-09-11, formerly `docs/BACKLOG.md` G35, same defect class and fix shape as G29 above) — its scope matches the flash log's own persistent lifetime, which is never reset by a start/stop cycle either. It does still start empty on every ESP32 boot (ordinary static zero-initialization, not rebuilt from the existing on-flash records at `wardriving_log_init()`), so a reboot mid-capture — never a same-session stop/restart — can still cause one extra duplicate flash append per address still in range at that moment. **The table itself was also restructured 2026-09-11 (formerly `docs/BACKLOG.md` G22)**: it used to be a single 128-slot table shared by both Wi-Fi and BLE addresses, hashed on the 6 raw address bytes with no type discriminator, so a Wi-Fi and a BLE address could alias to the same slot and silently evict each other's tracked RSSI/location state — logging the incoming observation as spuriously "new" and making the evicted address look spuriously "new" the next time it reappeared. It's now two separate tables (256 slots for Wi-Fi, 512 for BLE), sized against a real field capture that saw 517 distinct addresses in one session (172 Wi-Fi, 345 BLE), each using linear probing on an FNV-1a hash so a same-type collision no longer evicts a different address either — eviction now only happens if a table is genuinely full (every slot holds a distinct address), which the chosen sizes make rare rather than routine. This is a capacity/quality fix for the pre-log filter, not a wire-format or persisted-data change.
- **`gps`** (Phase 3, implemented and hardware-verified 2026-09-13) — poll-only current-fix status query, read via a UART-connected NEO-6M-class NMEA-0183 GPS module (RX-only; sending anything to the module is known to force it to re-acquire, so nothing is ever transmitted to it). Parses `GGA` (position, fix quality, satellite count, HDOP, MSL altitude) and `RMC` (date/time used for wardriving `utc_timestamp_s` field; speed/course are parsed but not yet surfaced in wardriving, backlogged separately). Reports one of three states: `no_signal` (no NMEA data ever received — a wiring/power problem), `acquiring` (valid NMEA traffic received, no valid fix yet — normal for up to minutes after cold start), or `fix` (both GGA fix quality > 0 and RMC status `A`). No fix-quality/HDOP/satellite-count threshold applies — any non-zero GGA fix quality counts as valid (a configurable threshold is backlogged). See [PROTOCOL.md](PROTOCOL.md)'s "`gps` command and status payloads" section for the exact wire shape.
- **`meshcore_scan`** (Heltec WiFi LoRa 32 V2 only, Phase 1 "detection + display", added 2026-09-26) — poll-only current-node-table status query for MeshCore (a third-party open LoRa mesh-network protocol, unrelated to this project's own BLE protocol), read passively via the board's onboard SX1276 LoRa radio (RadioLib-driven interrupt continuous receive, started unconditionally at boot, independent of the Wi-Fi/BLE radio the other capabilities contend over). Decodes only MeshCore's `ADVERT` (node advertisement) payload type at a single fixed EU-868 preset (869.525 MHz, 250 kHz bandwidth, SF11, CR 4/5, no frequency-hopping/multi-preset) — every other MeshCore payload type (chat, ack, path-return, etc.) is deliberately left unparsed; this is presence detection, not mesh participation. Each known node reports node ID (first 16 hex characters of its Ed25519 pubkey), name/role if advertised, RSSI (the LoRa radio's own reading for that frame, not anything in the packet), last-seen time, and lat/lon if advertised. A single `status` reply cannot list arbitrarily many nodes at once (the wire payload has to fit one unfragmented CBOR message, no partial/complete streaming exists for this capability) — it returns the most-recently-seen subset plus a `total_known_nodes` count so the Flipper can tell when the in-RAM table holds more than one reply shows. **Explicit scope cuts (Phase 1):** no flash persistence (RAM-only, cleared on reboot), no wdgwars.pl upload of any kind, no ADVERT signature verification (this capability trusts passively-observed broadcast data as MeshCore's own protocol intends — ADVERTs are signed but unencrypted specifically to allow passive listening, not to authenticate what a listener reports), no start/stop lifecycle (the radio always listens once booted; the only action is `status`). **No radio-coexistence validation exists between this board's LoRa radio and its separate Wi-Fi/BT combo radio** — see `docs/BACKLOG.md`. See [PROTOCOL.md](PROTOCOL.md)'s "`meshcore_scan` command and status payloads" section for the exact wire shape.
- **`gpio_control`** (later phase) — generic GPIO control. Reserves strapping/JTAG pins (GPIO0, 4, 5, 8, 9, 15) from generic control actions.
- **`zigbee`, `thread`** (later phase) — first as passive recon/sniffing capabilities matching the `wifi_scan`/`ble_scan` pattern (no joining or commissioning); active stack participation (joining as an end-device / Thread node) is a separately-scoped, much larger later effort.
- Display and generic/raw LoRa PHY capabilities remain out of scope for the Heltec WiFi LoRa 32 V2 pending their own dedicated design pass; `meshcore_scan` above is a narrower, already-specified exception (passively listening for a third-party mesh protocol's broadcast packets, not a general-purpose LoRa capability or a display driver) — see `docs/BASELINES.md`.

## Example capability record

```json
{
  "board": "esp32-c6-devkit",
  "board_id": "unique-board-id",
  "features": [
    "wifi_scan",
    "ble_scan",
    "wardriving",
    "gps"
  ],
  "firmware": "1.0.0"
}
```

The `board_id` travels in the authenticated protocol envelope; it is shown here to clarify the complete logical registry. `board_id` is derived from the chip's factory-programmed MAC address, avoiding collisions across multiple boards without a separate provisioning step. The Flipper app loads available actions from this registry instead of assuming every board behaves identically, and stores a separate pairing record per `board_id` — multiple boards may be paired to one Flipper at a time (see [PLAN.md](PLAN.md) "Multi-board pairing"). A board must reject a `command` for a capability absent from its advertised `features` list with `unsupported_capability`.

## Storage and persistence

The Flipper persists a board's capability registry in its own file per `board_id` (separate from the pairing-secret file). The capability record is queried exactly once — the first time runtime auth succeeds for that `board_id` AND no locally persisted capability file exists for it yet. The result is cached and never automatically re-queried on subsequent reconnects, even though this differs from the project's usual "distrust and re-verify every session" pattern used for authentication. This is a deliberate exception because a capability list is non-sensitive cached metadata, not a security credential. Nothing automatically invalidates or refreshes a persisted capability record; the only way to force a fresh query is a full unpair + re-pair. Unpairing a board deletes both its pairing record and its capability file together, as one operation — no orphaned capability file is left behind. The `board` and `firmware` fields are treated as opaque by the Flipper (no enum, no allowlist, no validation against known values) — they are hand-maintained constant strings per firmware build, not derived or validated values.
