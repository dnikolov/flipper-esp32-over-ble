# Capability registry

Connected ESP32 boards advertise an authenticated capability registry using the `capability_response` message defined in [PROTOCOL.md](PROTOCOL.md). Capability strings are stable lowercase ASCII identifiers using underscores. A board only advertises a capability it actually has the hardware for — see the phased roadmap in [PLAN.md](PLAN.md) step 7 for when each capability ships.

## Capabilities

- **`wifi_scan`** — Wi-Fi network scan, manually triggered by the Flipper user (a "Scan now" action, not automatic/periodic). Reports up to 32 discovered APs (the strongest by RSSI, if more are found), each with SSID, BSSID, RSSI, channel, supported PHY generation (802.11b/g/n/ax, collapsed to the highest generation the AP advertises), and auth mode. Results are shown on the Flipper's screen only — nothing is persisted or exported to SD card; that remains `wardriving`'s job. The ESP32-C6 has one 2.4GHz radio only (no 5GHz radio), so there is no separate "Wi-Fi 6 scan" mode — PHY generation is a per-AP property surfaced in the scan result, not a distinct scan operation. Uses the generic `command`/`status` message types — see [PROTOCOL.md](PROTOCOL.md)'s "`wifi_scan` command and status payloads" section for the exact wire shapes. Rejected `busy` if `wardriving`'s Wi-Fi source is currently active (one physical radio, one caller at a time).
- **`ble_scan`** — passive BLE advertisement scan, manually triggered by the Flipper user, mirroring `wifi_scan`'s "Scan now" pattern. Reports up to 32 discovered devices (the strongest by RSSI), each with address, address type, RSSI, and advertised name if present. Results are shown on the Flipper's screen only, nothing persisted. See [PROTOCOL.md](PROTOCOL.md)'s "`ble_scan` command and status payloads" section. Rejected `busy` if `wardriving`'s BLE source is currently active.
- **`wardriving`** — composite capability, advertised once the board has at least one of `wifi_scan`/`ble_scan` present. **Location data comes from a fixed-coordinate stub, not real GPS hardware, until a GPS module is physically wired to the board** (see [PLAN.md](PLAN.md) for the reorder decision and the swappable location-source interface this is built behind — every captured record currently carries the same hardcoded coordinate). A `command` to start it takes `sources` (`["wifi"]`, `["ble"]`, or both), `wifi_interval_ms`, and a `ble_window_ms`/`ble_interval_ms` pair in its `arguments` (a source the board does not have is rejected `invalid_command`); a `command` to stop it takes just an `action`. Interval bounds come from the radio-coexistence validation in [PLAN.md](PLAN.md) step 4, not a guessed value; the default itself is no longer step 4's most-aggressive point across the board — `ble_interval_ms`'s default was raised from 30ms to 500ms on 2026-09-10 after real wardriving traffic on real hardware showed 100% BLE duty starves the connection itself (`wifi_interval_ms`/`ble_window_ms` still default to their original point-4 values) — see [PROTOCOL.md](PROTOCOL.md) for the exact fields and current defaults. Capture runs autonomously once started — it continues across BLE disconnects and does not require an active Flipper connection to keep buffering, backed by a checksummed append-only circular log on a dedicated flash partition. Connecting drains the buffered backlog first (unsolicited, not waiting for a Flipper command — see PROTOCOL.md's `request_id = 0` convention), then streams live results. Because raw NOR flash can only be erased a whole sector at a time, "drop oldest when full" evicts a full sector's worth of records at once (tens of records in a batch), not strictly the single oldest record — see PROTOCOL.md's "Flash log eviction" note. Results captured before GPS achieves a real fix will be discarded once real GPS lands (a Flipper-settable backfill-to-first-fix option is backlogged, not implemented) — not applicable today since the stub always reports a fix. Data is transmitted as a compact CBOR record over BLE; the Flipper converts to WiGLE CSV only when writing to its SD card, as one timestamped file per flush session, written incrementally as records arrive (not buffered in RAM — a capture session may run for hours). The raw CBOR stream and flash log record every observation exactly as seen (no dedup at that layer); the CSV export layer alone collapses redundant repeats of the same address (`flipper/wardriving_csv.c`'s `feb_wardriving_dedup_should_write()`, added 2026-09-10): a row is written when an address is new this export session, its RSSI improved by >= 6dB since its last written row, or it has moved >= 30m since then (that last clause is real but inert today — real GPS hasn't landed yet, so distance from the fixed-coordinate stub to itself is always 0). A bounded 256-entry table tracks this per session; it evicts its oldest entry (not LRU) if a session sees more than 256 distinct addresses, which only softens dedup quality for an unusually address-dense run, not a correctness issue. `FirstSeen` timestamps in the exported CSV are reconstructed from the ESP32's boot-relative `timestamp_ms` by anchoring the newest drained record to the Flipper's current clock and backdating the rest — this board has no real-time clock, so exported times are an approximation, not a true wall-clock record.
- **`gpio_control`** (later phase) — generic GPIO control. Reserves strapping/JTAG pins (GPIO0, 4, 5, 8, 9, 15) from generic control actions.
- **`zigbee`, `thread`** (later phase) — first as passive recon/sniffing capabilities matching the `wifi_scan`/`ble_scan` pattern (no joining or commissioning); active stack participation (joining as an end-device / Thread node) is a separately-scoped, much larger later effort.
- Display and LoRa capabilities are planned for a second board (Heltec WiFi LoRa 32 V2 — a different chip family from the C6) in a later phase; see `docs/BASELINES.md`.

## Example capability record

```json
{
  "board": "esp32-c6-devkit",
  "board_id": "unique-board-id",
  "features": [
    "wifi_scan",
    "ble_scan",
    "wardriving"
  ],
  "firmware": "1.0.0"
}
```

The `board_id` travels in the authenticated protocol envelope; it is shown here to clarify the complete logical registry. `board_id` is derived from the chip's factory-programmed MAC address, avoiding collisions across multiple boards without a separate provisioning step. The Flipper app loads available actions from this registry instead of assuming every board behaves identically, and stores a separate pairing record per `board_id` — multiple boards may be paired to one Flipper at a time (see [PLAN.md](PLAN.md) "Multi-board pairing"). A board must reject a `command` for a capability absent from its advertised `features` list with `unsupported_capability`.

## Storage and persistence

The Flipper persists a board's capability registry in its own file per `board_id` (separate from the pairing-secret file). The capability record is queried exactly once — the first time runtime auth succeeds for that `board_id` AND no locally persisted capability file exists for it yet. The result is cached and never automatically re-queried on subsequent reconnects, even though this differs from the project's usual "distrust and re-verify every session" pattern used for authentication. This is a deliberate exception because a capability list is non-sensitive cached metadata, not a security credential. Nothing automatically invalidates or refreshes a persisted capability record; the only way to force a fresh query is a full unpair + re-pair. Unpairing a board deletes both its pairing record and its capability file together, as one operation — no orphaned capability file is left behind. The `board` and `firmware` fields are treated as opaque by the Flipper (no enum, no allowlist, no validation against known values) — they are hand-maintained constant strings per firmware build, not derived or validated values.
