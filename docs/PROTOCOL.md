# Protocol contract v2

This document defines the interoperable v2 protocol between the Flipper app and a paired ESP32. It is the source of truth for both implementations. Version 2 uses trusted-environment X25519 pairing and does not support earlier bootstrap protocols.

## Scope and transport

- The Flipper firmware service advertises the v2 primary service UUID `9c3f7e6a-f403-4c31-9ea2-58a7a20fb811`.
- The service exposes a write characteristic UUID `9c3f7e6a-f403-4c31-9ea2-58a7a20fb812` for ESP32-to-Flipper records and a notify characteristic UUID `9c3f7e6a-f403-4c31-9ea2-58a7a20fb813` for Flipper-to-ESP32 records.
- The ESP32-C6 scans for the advertised v2 service UUID, connects, writes records, and subscribes to notifications.
- Each protocol record is transmitted as one BLE application frame. Records that exceed the negotiated ATT payload are fragmented by a transport layer before protocol decoding; see [Fragmentation](#fragmentation).
- The initial maximum plaintext CBOR envelope is 512 bytes. Peers must reject larger envelopes with `error` code `payload_too_large`.
- All multi-byte integers in CBOR use native CBOR integer encoding; no fixed-endian byte encoding is used inside CBOR maps.

## Fragmentation

A protocol record whose encoded size exceeds the current negotiated ATT payload is split into fragments by a transport layer below CBOR decoding. Each fragment is prefixed with a 4-byte header, outside the CBOR envelope:

| Byte | Field | Meaning |
| --- | --- | --- |
| 0 | `flags` | Reserved; all bits `0` in this version. |
| 1 | `message_id` | Increments by one for each new message sent in a given direction; wraps at 256. Disambiguates which in-flight message a fragment belongs to. Carries no security meaning — that is the authenticated `sequence` counter's job. |
| 2 | `fragment_index` | 0-based index of this fragment within the message. |
| 3 | `fragment_count` | Total number of fragments in the message. |

Fragment payload capacity is the negotiated ATT MTU minus ATT/GATT write overhead minus this 4-byte header. One byte per field is sufficient given the fixed limits below (worst case, ATT MTU 23, yields well under 255 fragments for the largest permitted record) and given that write-with-response and a single active BLE connection mean only one message is ever being reassembled per direction at a time — the fragmentation layer does not need to support concurrent multiplexed messages.

Fixed limits:

- Absolute maximum encoded (post-fragmentation, pre-CBOR) record size: 768 bytes. This bounds the full on-wire record of either shape (unencrypted or protected) at the reassembly layer, before CBOR decoding begins — it is enforced independently of and prior to the 512-byte payload check below, and provides headroom for `session_id`, `board_id`, `sequence`, `tag`, and CBOR map/field overhead sitting alongside an encrypted `payload`.
- Maximum plaintext CBOR envelope: 512 bytes (see above). This bounds specifically the `payload` map's own canonical CBOR encoding — the plaintext that is encrypted into `ciphertext` on send, or decrypted from it on receive — not the full outer record. Reject a `payload` exceeding this with `error` code `payload_too_large`.
- One reassembly buffer per direction.
- 2-second reassembly timeout; an incomplete message is discarded if not fully reassembled within this window.

A receiver must reject, without allocating based on peer-controlled lengths: duplicate fragments, fragments with an inconsistent `fragment_count` for a `message_id` already in progress, fragments that would exceed the absolute maximum record size, an incomplete message left after the reassembly timeout, and out-of-order fragments (a fragment whose `fragment_index` does not match the next expected index for the in-progress `message_id` is rejected, not buffered for later reordering).

## Protocol versions and identifiers

- `version` is the unsigned integer `2` for this protocol.
- `board_id` is a stable, printable ASCII identifier unique to one physical ESP32. It is assigned during provisioning and must not be a mutable board model name.
- `session_id` is an 8-byte cryptographically random value generated by the ESP32 for every authenticated BLE session.
- A peer that receives an unsupported version must respond with an unencrypted `error` record with `code` `unsupported_version`, then close the BLE connection.

## Cryptographic requirements

- The trusted-environment X25519 BLE pairing ceremony is defined in [PAIRING.md](PAIRING.md). The resulting 32-byte `pairing_secret` is long-term pairing material and is never sent over BLE.
- Runtime records use AES-256-GCM. No other AES modes are permitted. (Originally specified
  as AES-128-GCM; revised during step 6 design when the Flipper's only exported raw-key
  AES-GCM primitive, `furi_hal_crypto_gcm_encrypt_and_tag`/`_decrypt_and_verify`, was found
  to be hardcoded to a 256-bit key at the hardware level — see `docs/PLAN.md` step 6's
  implementation decisions.)
- A fresh 32-byte session key is derived after authentication with HKDF-SHA-256:

  ```text
  session_key = HKDF-SHA-256(
      ikm = pairing_secret,
      salt = client_nonce || device_nonce,
      info = "flipper-esp32-over-ble/v2/aes-256-gcm" || board_id || session_id,
      length = 32)
  ```

- AES-GCM uses a 12-byte nonce: `session_id[0..7] || direction || sequence[0..2]`.
  - `direction` is `0x00` for Flipper-to-ESP32 and `0x01` for ESP32-to-Flipper.
  - `sequence` is an unsigned 24-bit counter encoded big-endian.
- A sequence counter begins at `1` for each authenticated session, increases by exactly one for every protected record in a direction, and must never wrap. A new BLE session is required before $2^{24} - 1$ protected records are sent.
- The AES-GCM authentication tag is 16 bytes. Authentication failure, an unexpected sequence, nonce reuse, or replay is fatal: discard the record and close the BLE connection without replying.
- The Additional Authenticated Data (AAD) is the canonical CBOR encoding of `{version, type, session_id, sequence, board_id}`. It is authenticated but not encrypted.
- The encrypted plaintext is the canonical CBOR encoding of `payload` only.

## Record format

All runtime records are canonical CBOR maps. The unencrypted connection and authentication records use the following shape:

```cbor
{
  "version": 2,
  "type": "hello" | "hello_ack" | "error",
  "session_id": h'0011223344556677',
  "board_id": "unique-board-id",
  "payload": { ... }
}
```

All protected records use this shape:

```cbor
{
  "version": 2,
  "type": "capability_query" | "capability_response" | "command" | "status" | "error",
  "session_id": h'0011223344556677',
  "board_id": "unique-board-id",
  "sequence": 1,
  "ciphertext": h'...',
  "tag": h'...'
}
```

`ciphertext` encrypts the `payload` map. Map keys are text strings. Implementations must produce canonical CBOR and must reject duplicate map keys, missing required fields, unexpected field types, and indefinite-length CBOR values.

### Canonical CBOR encoding (definition)

"Canonical" in this protocol does not mean general RFC 8949 deterministic/sorted-key encoding. Every record and payload map has a fixed, statically known field set per `type`. Canonical encoding for this protocol is defined as: **fields appear in exactly the order listed in this document's record-format and message-payload tables, with shortest-form CBOR integer/length encoding and no indefinite-length items.** Encoders must emit fields in that fixed order. Decoders must reject a map whose fields do not appear in that exact order, in addition to the already-specified duplicate-key and indefinite-length rejection.

This is a deliberate simplification over general canonical CBOR (RFC 8949 §4.2.1): the field sets here are fixed at compile time, so a general sorting algorithm buys nothing and only adds a second, independently-implemented sort to keep in sync between the two firmwares. It also has a concrete correctness reason: the AES-GCM AAD is the canonical CBOR encoding of `{version, type, session_id, sequence, board_id}`, and both peers must independently produce byte-identical AAD or every session fails authentication immediately — pinning one fixed field order removes any room for the two implementations to disagree.

## Session establishment

1. The ESP32 generates a new `session_id`, connects to the advertised BLE service, and sends unencrypted `hello` with payload `{ "client_nonce": bytes(16) }`.
2. The Flipper replies with unencrypted `hello_ack` with payload `{ "device_nonce": bytes(16), "proof": bytes(16) }`.
3. `proof` is the first 16 bytes of `HMAC-SHA-256(pairing_secret, "runtime-flipper" || S)`, where `S` is the canonical CBOR encoding of `{version, board_id, session_id, client_nonce, device_nonce}`.
4. The ESP32 verifies the proof and sends unencrypted `client_auth` with payload `{ "proof": bytes(16) }`, where `proof` is the first 16 bytes of `HMAC-SHA-256(pairing_secret, "runtime-esp32" || S)`.
5. Both peers verify the proofs, derive the session key, and begin protected records at sequence `1`.

The ESP32 must rate-limit failed authentication attempts. Neither peer sends application commands before this process completes. `hello`, `hello_ack`, and `client_auth` are not secret; their nonces, session identifier, board identifier, and proofs bind the BLE connection to the stored pairing secret.

### Runtime auth failure handling

Two distinct failure modes exist at this step, and a peer must not conflate them:

- **Unknown board.** If the Flipper has no stored pairing record for the `board_id` carried in `hello`, it cannot compute `proof` at all. It replies with unencrypted `error` code `unknown_board` (using the pairing-record wire envelope shown below, since no `session_id` exists yet) and takes no further action. This is the normal, expected outcome the first time an ESP32 with a stored secret talks to a Flipper that has never paired it (or no longer has — see [PLAN.md](PLAN.md) step 6's reset-vs-runtime-auth design). On receiving `unknown_board`, the ESP32 treats this as authorization to fall back to the reset-gated pairing flow defined in [PAIRING.md](PAIRING.md), opening a fresh pairing window on its next attempt.
- **Proof verification failure.** If either peer has a record for the `board_id` but the computed `proof` does not match (the ESP32 verifying `hello_ack`'s proof, or the Flipper verifying `client_auth`'s proof), this indicates the two stored secrets have desynced, been corrupted, or a peer is being impersonated — a real anomaly, not the "never paired" case. The verifying peer closes the connection without a reply (matching the general authentication-failure handling under "Cryptographic requirements" below) and counts it against the existing rate-limit requirement above. **A peer must not fall back to opening a pairing window on a proof failure** — recovery requires an explicit, deliberate action (the Flipper's local unpair action, or erasing the ESP32's stored secret), not automatic renegotiation. Treating a proof failure the same as `unknown_board` would let a radio attacker force repeated pairing-window openings simply by corrupting proofs in transit.

## Initial pairing records

Pairing records are unencrypted canonical CBOR maps accepted only during the ESP reset-gated pairing window defined in [PAIRING.md](PAIRING.md). Pairing uses X25519 and HKDF-SHA-256. It is intentionally unauthenticated; its use is limited to the trusted environment described in the pairing flow.

Let `T` be the canonical CBOR encoding of `{version, service_uuid, board_id, pairing_epoch, client_nonce, device_nonce, esp32_public_key, flipper_public_key}`. `service_uuid` is the 16-byte UUID value of the v2 primary service, in RFC 4122 big-endian order matching this document's string form (`9c3f7e6a-f403-4c31-9ea2-58a7a20fb811` -> bytes `9c 3f 7e 6a f4 03 4c 31 9e a2 58 a7 a2 0f b8 11`). Each implementation must explicitly convert its BLE stack's native in-memory UUID representation to this order before building `T` — do not assume it already matches; a prior UUID-byte-order mismatch already caused a real bug in the step 2 transport (see `docs/SESSION_MEMORY.md`), and `T` is exactly as sensitive to this since both peers must derive byte-identical confirmations from it. Implementations must reject an invalid protocol version, field, or X25519 public key.

### Pairing record wire envelope

Every pairing record (`pair_init`, `pair_reply`, `pair_confirm`, `pair_complete`) and every pairing-phase `error` record (`pairing_disabled`, `pairing_failed`, `pairing_expired`) uses this envelope — the general unencrypted-record shape shown above, minus `session_id`, which does not exist until the runtime `hello` flow begins:

```cbor
{
  "version": 2,
  "type": "pair_init" | "pair_reply" | "pair_confirm" | "pair_complete" | "error",
  "board_id": "unique-board-id",
  "payload": { ... }
}
```

`payload` holds exactly the fields listed in the table below for `pair_init`/`pair_reply`/`pair_confirm`/`pair_complete`, or `{code, message?, request_id?}` for a pairing-phase `error`. `board_id` is present on every pairing record, including ones sent before pairing is confirmed — it identifies which attempt this is. Runtime-phase `error` records (sent after a session exists) continue to use the original `session_id`-bearing envelope; a decoder distinguishes the two shapes by connection phase (whether a session currently exists), not by record content.

| Type | Direction | Required payload fields | Authentication |
| --- | --- | --- | --- |
| `pair_init` | ESP32 -> Flipper | `pairing_epoch`: bytes(16), `device_nonce`: bytes(16), `esp32_public_key`: bytes(32) | None |
| `pair_reply` | Flipper -> ESP32 | `client_nonce`: bytes(16), `flipper_public_key`: bytes(32), `confirmation`: bytes(32) | HMAC-SHA-256 confirmation derived from `K_shared` |
| `pair_confirm` | ESP32 -> Flipper | `confirmation`: bytes(32) | HMAC-SHA-256 confirmation derived from `K_shared` |
| `pair_complete` | ESP32 -> Flipper | `confirmation`: bytes(16) | HMAC-SHA-256 completion tag derived from `K_shared` |

`esp32_public_key` and `flipper_public_key` are 32-byte X25519 public keys. Each peer generates a fresh X25519 private key for every attempt, rejects an all-zero shared secret, and compares confirmations in constant time.

After both confirmations validate, derive `pairing_secret` as:

```text
pairing_secret = HKDF-SHA-256(
  ikm = K_shared,
  salt = pairing_epoch || client_nonce || device_nonce,
  info = "flipper-esp32-over-ble/v2/x25519-pairing-secret" || board_id,
  length = 32)
```

Define `K_confirm = HKDF-SHA-256(ikm = K_shared, salt = pairing_epoch, info = "flipper-esp32-over-ble/v2/pair-confirm", length = 32)`. In `pair_reply`, the Flipper sends `HMAC-SHA-256(K_confirm, "flipper-confirm" || T)`. After verifying it, the ESP32 sends `HMAC-SHA-256(K_confirm, "esp32-confirm" || T)` in `pair_confirm`. The ESP32 atomically persists `pairing_secret` before sending `pair_complete`, whose confirmation is the first 16 bytes of `HMAC-SHA-256(K_confirm, "complete" || T)`. The Flipper persists `pairing_secret` only after verifying this tag. `K_shared`, `K_confirm`, X25519 private keys, and session keys must be zeroized after every success or failure.

Outside an open window, `pairing_disabled` is the sole response to a pairing record. During a pairing attempt, use `pairing_failed` for all invalid public-key, shared-secret, and confirmation failures; do not expose the cause. `pairing_expired` reports an elapsed pairing window.

## Message payloads

| Type | Direction | Required payload fields | Meaning |
| --- | --- | --- | --- |
| `capability_query` | Flipper -> ESP32 | `requested`: array of text strings, optional | Requests the complete registry when omitted or an allowed subset when present. |
| `capability_response` | ESP32 -> Flipper | `board`: text, `firmware`: text, `features`: array of text strings | Reports the board model, firmware version, and supported capabilities. |
| `command` | Flipper -> ESP32 | `capability`: text, `request_id`: unsigned integer, `arguments`: map | Invokes one advertised capability. |
| `status` | ESP32 -> Flipper | `request_id`: unsigned integer, `state`: text, `result`: map, optional | Reports command progress, completion, or data. |
| `error` | either | `code`: text, `message`: text, optional `request_id`: unsigned integer | Reports a recoverable application or protocol error. |

Defined `error.code` values are `unsupported_version`, `malformed_record`, `payload_too_large`, `unsupported_capability`, `invalid_command`, `busy`, `internal_error`, `pairing_disabled`, `pairing_expired`, `pairing_failed`, and `unknown_board` (see "Runtime auth failure handling" above).

**Notes on capability discovery:** The `requested` field on `capability_query` is defined but currently unimplemented — the ESP32 always returns the full registry regardless of what's sent (or not sent), and the Flipper always omits the field. This is flagged as a backlog item to revisit once there's a real multi-capability use case that would benefit from partial queries. The `board` and `firmware` fields in `capability_response` are hand-maintained constant strings per firmware build (not derived or validated), and the Flipper receives them as opaque values — no enum, no allowlist, no validation against known values. Capability gating is driven entirely by the `features` array, never by the `board` string.

## Reliability and reconnect behavior

- BLE delivery is treated as ordered within an active connection; protocol records are not retransmitted automatically.
- A sender may retry an idempotent `command` only with a new sequence number and the same `request_id` after reconnecting and establishing a new session.
- ESP32 implementations should retain a bounded cache of recently completed `request_id` values for the current session to avoid repeating non-idempotent work after a duplicate request.
- A peer closes an idle authenticated connection after 30 seconds without a record. Either peer may reconnect and establish a new session.

## Implementation security requirements

- This protocol defends against a remote/radio adversary who does not have physical possession of either paired device. Physical possession of the Flipper or the ESP32 is explicitly out of scope for the current phase: treat a lost or stolen paired device as fully compromising that one pairing relationship, and reset (ESP32) or unpair (Flipper) immediately. Other stored pairings (see multi-board pairing in [PLAN.md](PLAN.md)) are unaffected.
- The ESP32 stores `pairing_secret` in a dedicated NVS namespace with a version, validity marker, and atomic replacement procedure (see [PLAN.md](PLAN.md)). Secure Boot, flash encryption, and NVS encryption are deferred hardening for a later phase, not a current requirement — see [PLAN.md](PLAN.md) "Deferred: hardware hardening."
- The Flipper stores `pairing_secret` via atomic app-owned storage (temporary file, exact write verification, `storage_file_sync()`, close, rename) — not a hardware-backed secret vault. Local SD-card, debug-mode, or modified-firmware access to a Flipper recovers its stored pairing material; this is an accepted limitation of the standalone-FAP delivery model (see [STANDALONE_FAP.md](STANDALONE_FAP.md)), not an oversight to close in this phase.
- Do not log secrets, derived keys, nonces, plaintext, or authentication tags on either device, regardless of storage hardening level.
- Cryptographic comparisons, including `proof` and authentication tags, must be constant-time where the platform API provides a suitable primitive.
- A factory reset or explicit unpair deletes the stored `pairing_secret` and all pairing metadata for that one board only; other stored pairings are unaffected.
