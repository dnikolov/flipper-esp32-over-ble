# BL06 findings (2026-09-13)

## Summary

The BL06 issue is not a simple missing reconnect branch. It is a state-machine race in the ESP32's BLE wardriving reconnect path: the discovery re-arm timer can re-enter discovery while a connect attempt is already pending, and the code path that handles BLE advertisements does not have a single shared invariant to prevent duplicate connect attempts or connect-while-discovering overlap.

The initial patch I tried added a `wardriving_ble_connect_in_flight` guard and reset logic in the BLE discovery and connect pathways. That patch reduced the obvious overlap, but live behavior still showed the reconnect stall in the field, which means the fix was only partial and not sufficient for BL06.

## What I observed

Evidence from the live ESP log during the reconnect repro showed this successful pattern when the reconnect path is working:

- `idle authenticated connection ... terminating`
- `disconnected: reason=534`
- `found v2 peer, connecting`
- `connected; exchanging MTU`
- `client_auth sent; runtime session authenticated`

The failure pattern we kept reproducing was:

- board enters a wardriving BLE discovery loop
- Flipper is taken out of range and then brought back in
- no `found v2 peer, connecting` line appears in the expected reconnect window
- the Flipper LED goes dark and the session stays disconnected

That means the reconnect trigger is not reliably firing when the connection is re-established after a disconnect while wardriving is active.

## Root cause hypothesis

The underlying problem is a shared-state race between:

1. the wardriving BLE timer callback re-arming discovery (`wardriving_ble_interval_cb()`), and
2. the advertisement match path (`BLE_GAP_EVENT_DISC`) attempting a `ble_gap_connect()`.

There are two important issues in that interaction:

- The timer callback is trying to restart discovery without checking whether a BLE connect is already in progress.
- The advertisement match path itself is not protected by a single shared invariant that prevents a second connect when the discovery window is being re-armed or when a connect is already pending.

The live logs strongly suggest the bug is timing-sensitive, not deterministic: discovery restarts are happening on a cadence that can overlap with the pending connect, which keeps the device from making a clean, authenticated reconnect.

## Why the first guard was not enough

The temporary `wardriving_ble_connect_in_flight` guard prevented a narrow class of duplicate connect attempts, but it did not fully resolve the reconnect state machine. Specifically:

- it existed only in the wardriving timer path and the discovery-match path, not as a single shared invariant at every entry point,
- it did not address the broader possibility that the disconnect cleanup and reconnect scheduling still leave the system in a stale state,
- it did not eliminate the reconnect stall in live testing when the Flipper was moved back into range.

This aligns with the project lesson captured earlier: a guard must be enforced at the shared entry point, not just in one caller, and a reconnect path must be verified against real hardware evidence rather than assumed to work from code review alone.

## Conclusion

BL06 remains a real reconnect-state bug in the wardriving BLE path. The attempted guard was a valid investigation step, but it was not the final fix. The code should be reverted to the prior state until a complete fix is identified and verified against the actual disconnect/reconnect workflow.

This file documents the findings without leaving the code in a partial attempted fix state.
